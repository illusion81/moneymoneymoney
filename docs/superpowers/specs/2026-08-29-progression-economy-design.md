# Progression Economy Design

## Goal

Add a progression layer on top of the existing wealth forest loop: experience points that raise a profile level, cosmetic coins earned from real financial behaviour, a shop where coins buy skins, and a paid restoration path that clears a withered tree instead of leaving it as a permanent mark.

This extends `ForestEngine`, `HomeScreen`, and `AchievementsScreen`. It does not change `ReportGenerator` or the onboarding questionnaire.

## Scope

All balances, prices, and awards are computed locally in Dart from existing check-in records. There is no external service, no server authority, and no real-money purchase of any kind.

Persistence remains out of scope, consistent with the base MVP. Progression state lives in memory alongside `ForestSummary` and is recomputed or carried by the app shell.

## Design Principles

These constrain every rule below.

- **Coins are cosmetic only.** They are non-cash, non-tradeable, non-refundable, and cannot be bought with money. They unlock appearance, never financial features, advice, or data.
- **Awards are deterministic and auditable.** Every XP and coin award is a pure function of `ForestDay` records the user already produced. Nothing is random, and nothing is generated by a language model.
- **XP never decreases.** A missed day earns zero, never a penalty. Financial setbacks must not read as debt to the app.
- **Restoration repairs the visual and the streak, not the record.** A restored day never counts as a healthy day and never retroactively pays XP or coins. This keeps the honesty of the underlying data intact and stops coins from becoming a way to buy a fake track record.

## Model Additions

### Tree Status

`TreeStatus` gains a fourth value:

```
enum TreeStatus { pending, healthy, withered, restored }
```

`restored` is only ever produced by an explicit restoration action. The check-in path can still only produce `healthy` or `withered`.

### Forest Day

`ForestDay` gains two fields:

- `restoredAt`: `DateTime?`, null unless the day was restored.
- `recoveryNote`: `String?`, the user's short explanation supplied at restoration time.

Existing fields are unchanged, so all current check-in behaviour and tests stay valid.

### Progression State

New model file `lib/models/progression.dart`:

- `enum RewardEventType { healthyDay, underBudget, streakMilestone, achievementUnlock, levelUp, restorationSpend, purchaseSpend }`
- `class RewardEvent { DateTime date; RewardEventType type; int xp; int coins; String description; }` — coins are negative for spends.
- `class LevelProgress { int level; int xpIntoLevel; int xpForNextLevel; double fraction; }`
- `class ProgressionState { int totalXp; LevelProgress level; int coinBalance; int lifetimeCoinsEarned; int lifetimeCoinsSpent; List<RewardEvent> ledger; }`

The ledger is the audit trail. Every award and every spend appends one entry, and `coinBalance` must always equal `lifetimeCoinsEarned - lifetimeCoinsSpent`.

### Shop

New model file `lib/models/shop_item.dart`:

- `enum ShopItemCategory { treeSkin, ground, sky }`
- `class ShopItem { String id; String name; String description; ShopItemCategory category; int price; int requiredLevel; bool isDefault; }`
- `class ShopState { Set<String> ownedItemIds; Map<ShopItemCategory, String> equippedItemIds; }`
- `enum PurchaseFailure { alreadyOwned, insufficientCoins, levelTooLow, unknownItem }`
- `class PurchaseResult { bool success; PurchaseFailure? failure; ShopState state; ProgressionState progression; String message; }`

## XP Rules

`ProgressionEngine` computes XP by replaying the full day list. It is a pure function of `List<ForestDay>` plus the achievement list, so the same history always yields the same level.

Per-day awards, healthy days only:

- Base healthy day: **10 XP**.
- Streak bonus: **2 XP** for each consecutive healthy or restored day before this one, capped at **20 XP**. Formula: `min(streakBeforeToday, 10) * 2`.
- Under-budget bonus: **5 XP** when `spending <= dailyBudget * 0.8`.

Maximum from a single day is 35 XP.

Other awards:

- Achievement unlock: **25 XP**, once per achievement.
- Withered day: **0 XP**.
- Restored day: **0 XP**. Restoration never pays.

### Level Curve

XP required to advance from level `L` to `L + 1`:

```
xpToAdvance(L) = 100 + 50 * (L - 1)
```

Cumulative XP required to have reached level `L`:

```
totalXpForLevel(L) = 100 * (L - 1) + 25 * (L - 1) * (L - 2)
```

Worked values: level 2 at 100 XP, level 3 at 250, level 4 at 450, level 5 at 700, level 6 at 1000.

The formulas are authoritative. `totalXpForLevel` is by construction the cumulative sum of `xpToAdvance`, and any worked value in this document that disagrees with them is an error in the document, not a second intended curve.

Levels start at 1 and cap at 50. XP continues to accumulate past the cap but the level stays at 50 and no further level-up coins are paid.

## Coin Rules

Coins are awarded on the same replay pass, from the same records.

Earnings:

- Healthy day: **5 coins**.
- Under-budget day, `spending <= dailyBudget * 0.8`: **+3 coins**.
- Streak milestone, awarded once each time the streak reaches the value: **3 days → 15**, **7 days → 30**, **14 days → 60**, **30 days → 120**.
- Achievement unlock: **20 coins**, once per achievement.
- Level up: **25 × the new level** coins.
- Withered day: **0 coins**.
- Restored day: **0 coins**.

Spends:

- Restoration, per the cost table below.
- Shop purchase, at the item's listed price.

A steady user earning healthy days at roughly 8 coins per day plus milestones reaches the first mid-tier skin in a little under three weeks, which is the intended pacing.

## Restoration Rules

Restoration is the mechanic that replaces permanent withering. It clears the withered tree visual, repairs the streak, and preserves the honest record underneath.

### Eligibility

A day can be restored when all of the following hold:

- Its status is `withered`.
- Its date is within the last **7 days** inclusive of today.
- It has not already been restored.
- The user has fewer than **2 restorations** in the trailing 30 days.
- The user supplies a non-empty recovery note.
- The coin balance covers the cost.

### Cost

Cost escalates with prior restorations inside the trailing 30-day window:

```
restorationCost(priorRestorationsInWindow) = [60, 150][priorRestorationsInWindow]
```

A third restoration in the same window is not purchasable at any price. This is deliberate: the cap keeps restoration a relief valve rather than a way to buy an unbroken record.

### Effect

On success:

- The day's status becomes `restored`, `restoredAt` is set, and `recoveryNote` is stored.
- `treeLevel` is set to 1 so the tree renders as a small recovering sapling rather than a withered one.
- The coin cost is deducted and a `restorationSpend` ledger entry is appended.
- No XP and no coins are awarded for the restored day.
- The summary is recomputed, which repairs the streak.

The day's original `message` is preserved and the UI shows it beneath the recovery note, so the user can always see what actually happened.

### Streak And Counting

- `_currentStreak` counts a day as continuing when its status is `healthy` **or** `restored`.
- `healthyTreeCount` counts only `healthy` days. Restored days are excluded.
- `witheredTreeCount` counts only days still `withered`. A restored day leaves this count.
- `ForestSummary` gains `restoredTreeCount`.
- `_hasRecoveryDay` treats a preceding `withered` **or** `restored` day as qualifying, so the Recovery Day achievement stays reachable after a restoration.

### Purchase Rules

- Purchase requires `coinBalance >= price` and `level >= requiredLevel`. Both are checked, and the failure reason is reported specifically.
- Purchasing an owned item fails with `alreadyOwned` and never deducts coins.
- Purchase is atomic: coins deduct, the id enters `ownedItemIds`, and a `purchaseSpend` ledger entry appends, or nothing changes.
- A purchased item is **not** auto-equipped. Equipping is a separate free action.
- Equipping sets `equippedItemIds[category]`, replacing whatever was there. Exactly one item is equipped per category at all times.
- There is no selling, refunding, or trading.

## Achievement Additions

Three achievements are added to the existing five:

- **Second Wind** (`second-wind`): restore a day. Unlocks the first time any day reaches `restored` status. This deliberately rewards recovery rather than shaming the miss.
- **Curator** (`curator`): own any non-default cosmetic item.
- **Seedling Scholar** (`seedling-scholar`): reach level 5.

Because Curator and Seedling Scholar depend on shop and progression state, `ForestEngine.summarize` gains optional `progression` and `shopState` parameters. When they are omitted the two new achievements report locked, which keeps every existing call site and test valid.

## Engine Interfaces

### ProgressionEngine

```
class ProgressionEngine {
  ProgressionState compute({
    required List<ForestDay> days,
    required List<Achievement> achievements,
    required List<RewardEvent> spendEvents,
  });

  LevelProgress levelForXp(int totalXp);
  int totalXpForLevel(int level);
  int xpToAdvance(int level);
}
```

`compute` replays the entire history from scratch each call. Spends are passed in rather than derived, because they are user actions rather than a function of the forest record. The result is fully determined by its inputs.

### ForestEngine Additions


## Screens

### Home Screen Changes

Add above the tree card:

- A level chip reading `Level 4`, an XP bar showing `xpIntoLevel / xpForNextLevel`, and the numeric pair beneath it.
- A coin balance pill with a coin icon, keyed `coin-balance`.

The tree card renders the equipped tree skin, ground, and sky rather than the fixed icon set. Tree level still selects the growth stage within the equipped skin.

Below the tree card, when the latest day is `withered`:

- A restoration panel showing the cost, remaining restorations in the window, a note field keyed `recovery-note-field`, and a button keyed `restore-button` labelled `Restore for N coins`.
- When restoration is not eligible, the panel shows the blocking reason as plain text and no button. It never shows a paywall-style upsell.

When the latest day is `restored`, the status text reads `Restored tree` and the recovery note is shown under the original message.

Add a shop entry point to the app bar, alongside the existing report and achievements icons.

After a successful check-in, a summary line reports what was earned, for example `+15 XP, +8 coins`.

### Shop Screen

New file `lib/screens/shop_screen.dart`.

- Title `Forest Shop`.
- Header with coin balance and current level.
- Sections per category with the category name.
- Each item is a card showing name, description, price, and one of: `Equipped`, `Equip`, `Buy` with the price, or `Level N required` when locked by level.
- Insufficient coins renders the buy button disabled with the price still visible, so the user can see what they are working toward.
- Failure feedback appears inline as a snack bar carrying `PurchaseResult.message`.
- `Back to Forest` button.

### Achievements Screen Changes

- Add a progression card at the top showing level, XP bar, and coin balance.
- Extend the existing progress row to four tiles: current streak, healthy trees, restored trees, withered trees.
- Render all eight achievements from `ForestSummary.achievements` unchanged.
- Add a collapsible recent-activity list rendering the last 10 `RewardEvent` entries with date, description, and signed XP and coin deltas. This is the user-facing audit trail.

### App Shell Changes

`AppView` gains `shop`. `_MyAppState` gains:

- `ProgressionState _progression`
- `ShopState _shopState`
- `final List<RewardEvent> _spendEvents`

After every check-in, restoration, or purchase, the shell recomputes progression from the full day list and the accumulated spend events, then recomputes the summary with progression and shop state supplied.

## Error Handling

- Empty or whitespace-only recovery note blocks restoration with an inline message.
- Insufficient coins blocks restoration and purchase, reporting the shortfall.
- A restoration attempt on an ineligible day is refused with the specific reason: too old, already restored, not withered, or window limit reached.
- Level-gated purchases report the required level rather than a generic failure.
- Coin balance can never go negative. Any operation that would take it below zero is refused before any state changes.

## Testing Requirements

Unit tests, `test/progression_engine_test.dart`:

- Level thresholds match the closed-form table at levels 1 through 6.
- A single healthy day under budget awards 15 XP and 8 coins.
- A three-day healthy streak awards the streak milestone coins exactly once.
- Withered and restored days award zero XP and zero coins.
- Coin balance equals lifetime earned minus lifetime spent after a mixed sequence.
- Level-up coins scale with the new level.

Unit tests, extending `test/forest_engine_test.dart`:

- A withered day within 7 days quotes a cost of 60 on the first restoration.
- The second restoration in the window quotes 150.
- A third restoration in the window is refused.
- A withered day older than 7 days is refused.
- Restoration sets status to `restored`, repairs the streak, decrements the withered count, and does not increment the healthy count.
- Restoration with an empty note is refused and leaves state unchanged.
- Recovery Day still unlocks for a healthy day following a restored day.

Unit tests, `test/shop_service_test.dart`:

- Purchase succeeds and deducts coins when balance and level both suffice.
- Purchase fails with `insufficientCoins` and leaves the balance untouched.
- Purchase fails with `levelTooLow` for a level-gated item.
- Re-purchasing an owned item fails with `alreadyOwned` and does not deduct.
- Equipping replaces the previous item in the same category only.
- Default items are owned and equipped in `initialState`.

Widget tests, extending `test/widget_test.dart`:

- The home screen shows the level chip and coin balance after starting the plan.
- A successful check-in increases the displayed coin balance.
- An overspending check-in shows the restoration panel.
- Restoring with a note changes the status text to `Restored tree`.
- The shop screen lists catalog items and disables the buy button when coins are short.

## Future Extension Points

- Move award computation and balances to a server-authoritative service before any public release. The current client-side model is trivially manipulable and is acceptable only for a local MVP.
- Add persistence for `ProgressionState`, `ShopState`, and the spend ledger together with the day records, so balances survive restart.
- Add seasonal or limited-time cosmetics once the base catalog proves engaging.
- Add a free weekly streak shield as an alternative to paid restoration, so users with low balances are not excluded from recovery.
- Revisit the economy constants after real retention data. Every award value in this document is a starting guess and should be tuned, not treated as settled.

## Explicit Non-Goals

- No real-money purchase of coins, and no in-app purchase integration.
- No conversion of coins to cash, rewards, discounts, or anything of financial value.
- No cosmetic or progression gate on financial guidance, reporting, or data access.
- No leaderboard or social comparison in this version.
